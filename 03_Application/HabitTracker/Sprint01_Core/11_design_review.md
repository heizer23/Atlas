## Blocking Issues

| # | Location | Rule / Contract Violated | Required Change |
|---|----------|--------------------------|-----------------|
| 1 | `10_architecture.json` §`interfaces.exposed_surfaces` "GET /api/habittracker/reports" (`ui_contract`, `query_behavior.row_shape`) and §`internal_flow` step 11; `10_scaffolding.json` `backend/routers/reports.py` role text | R-CON-BP-08 (Contract Self-Containment), R-CON-BP-04 (UI Data Contract — Contract Authority) | The design states `GET /reports` returns "Dataset ... PLUS one additive top-level sibling field ... period_summary" but never specifies the technical mechanism that attaches it. The canonical `platform_contracts.Dataset` (`02_Platform/packages/platform_contracts/contracts.py`) is a pydantic `BaseModel` with exactly `meta`/`schema_`/`rows` and no `extra="allow"` in its `model_config`. Passing `period_summary` as a constructor kwarg to `Dataset(...)` is silently dropped (pydantic's default `extra="ignore"` behavior) — it would not appear in the serialized response at all, breaking the Reports screen's period-level summary with no error. A working precedent already exists in this codebase (`03_Application/EssayCards/backend/routers/review_stats.py::get_review_stats_summary`: route declares `response_model=None`, builds `content = dataset.model_dump(by_alias=True, mode="json")`, then returns a manually constructed `JSONResponse`) but is not referenced anywhere in this design. Name the exact mechanism explicitly in `10_architecture.json` §`internal_flow` step 11 and in `10_scaffolding.json`'s `reports.py` entry (e.g., adopt the `response_model=None` + `dataset.model_dump()` + dict-merge pattern, or an equivalent concretely-specified alternative) so the contract is self-contained and does not depend on an implementer independently rediscovering an unreferenced precedent. |

## Non-Blocking Issues

| # | Location | Observation |
|---|----------|-------------|
| 1 | `00_draft.md` §Defaults and Merging; `10_architecture.json` §`contracts.invariants` (Checked-value rule); §`internal_flow` step 7 (Draft branch) | A Draft (not-yet-confirmed) day's displayed habit list is always recomputed from the habit's CURRENT active window (`resolve_active_habits_for_date`), never from which habits already have saved `habit_results` rows for that date. If a habit is archived (`end_date` set before the draft's date) after a checkbox value was already draft-saved for it, that habit silently disappears from the Daily Review screen on reopen, and `compute_expected_habit_ids` subsequently excludes it from the expected set on the next PUT — the orphaned `habit_results` row is never shown or reconciled again. This edge case is not addressed by the draft or by `contracts.invariants` (contrast with the Confirmed-day case, which is explicitly frozen and immune to this). Not blocking — rare in a single-user app — but worth an explicit non-goal statement or resolution in a follow-up pass. |
| 2 | `10_scaffolding.json` `backend/routers/habits.py`, `reviews.py`, `reports.py` `public_objects` | No `ColumnSchema` constants (e.g. `HABIT_SCHEMA`) are scaffolded for any of the three Dataset-returning routers, unlike the established convention elsewhere in the codebase (e.g. EssayCards' `REVIEW_STATS_SUMMARY_SCHEMA`/`ACTIVITY_SCHEMA` module-level constants in `review_stats.py`). Row shapes are fully specified in prose (`exposed_surfaces.row_shape`), so this does not block implementation, but adding the schema constants to the scaffold would keep the stub closer to the module structure the implementer will actually produce. |
| 3 | `10_architecture.json` §`open_questions[0]` and §`open_questions[1]` | Both correctly surfaced with an owner (architecture; product) per the Ambiguity Handling requirement. `open_questions[0]` (should `period_summary` eventually become a versioned platform Dataset extension) is a legitimate longer-term question distinct from Blocking Issue #1 above, which only requires specifying this sprint's immediate technical mechanism. No action required for this sprint beyond resolving #1. |

## Approval Condition

`10_architecture.json` §`internal_flow` step 11 and `10_scaffolding.json`'s `backend/routers/reports.py` entry must name the explicit technical mechanism by which `GET /api/habittracker/reports` attaches `period_summary` alongside the `meta`/`schema`/`rows` Dataset triad (e.g. `response_model=None` + manual `dataset.model_dump()` dict assembly, following the `review_stats.py` precedent, or an equivalent concretely-specified alternative), so the contract is self-contained per R-CON-BP-08 and does not rely on an implementer independently discovering an unreferenced codebase precedent.

### Verification notes (supporting detail, non-blocking)

- **R-CON-AL-01 (query behavior explicitness):** Verified for all three parameterized endpoints (`GET /habits`, `GET /reviews/{date}`, `GET /reports`) — each `query_behavior` block in `10_architecture.json` explicitly states supported parameters, defaults, allowed combinations, ordering, grouping, time basis, boundary construction, empty-result behavior, and zero-fill behavior. `GET /reports` in particular resolves ownership of boundary construction (week = ISO Monday–Sunday, month = calendar month, both Europe/Berlin) and states `anchor_date` is always required with no implicit server-side "today" fallback. The one gap found is the structural `period_summary` mechanism (Blocking Issue #1) — a R-CON-BP-04/R-CON-BP-08 completeness issue, not an R-CON-AL-01 explicitness issue; the query-behavior prose itself is complete.
- **R-CON-AL-02 (scope-mode closure):** Verified — `period` × `anchor_date` has no invalid combination; every value of `period` (`week`/`month`) is independently constructible via `resolve_report_period`, and `rows: []` is an explicitly valid, non-error output for a period with zero active habits.
- **R-CON-AL-03 (invariant realizability):** Verified — every declared invariant (frozen confirmed display, draft/unreviewed merge, four-way cell state, period stats) is backed by a named function or SQL fragment in `internal_flow`, with no undeclared pre-queries or hidden defaults.
- **R-CON-AL-04/05 (partial update semantics / round-trip completeness):** Verified — `PATCH /habits/{habit_id}` correctly uses `model_fields_set` to distinguish omitted from explicit-null, rejects explicit null on NOT NULL columns (`name`/`default_checked`/`active_from`), and accepts omit/null/value tri-state on nullable columns (`description`/`end_date`). All four round-trip aspects (UI empty-state, payload, backend interpretation, persisted state) are defined in `deferrals.ui_implementer` and `contracts.failure_modes`, matching `10_test_spec.md`'s dedicated scenarios.
- **R-CON-AL-06 (time authority):** Verified — Europe/Berlin is the sole authority for every calendar-date concept, computed server-side via stdlib `zoneinfo` (`berlin_today()`); the client only ever sends explicit `date`/`anchor_date` strings, never a raw timestamp or "is today" boolean.
- **R-CON-BP-01/02 (architecture as AI interface / contracts and boundaries):** Verified — public interfaces, failure modes, and the canonical `review_logic.py` module (single source of truth for the three pieces of "real logic": active-habits-for-date, expected-set, period-boundary resolution) are explicit and named consistently across `10_architecture.json` and `10_scaffolding.json`.
- **R-CON-BP-04 (UI Data Contract, excluding Blocking Issue #1):** Verified — mutation endpoints are correctly marked `ui_contract: none` with typed success bodies and `ApiError` failures; `GET /habits` and `GET /reviews/{date}` are plain, uncomplicated `Dataset` responses; the synthetic `id = review_date` for an Unreviewed day's single-row Dataset correctly satisfies the row-identity requirement.
- **R-CON-BP-06 (consumer pattern fidelity):** Verified — `src/shellConfig.ts` registration and the `main.tsx` side-effect import are both explicitly named in `deferrals.ui_implementer`/`application_implementer`, matching the exact StoryReader precedent the sprint log confirms was read during design.
- **R-CON-BP-07 (canonical artifact path):** Verified — `10_schema.sql` is referenced consistently as the canonical schema source, promoted verbatim to `schema.sql` at the component root per `10_scaffolding.json`, read by `backend/database.py::init_schema()` — no inline-DDL drift of the kind previously found in TaskTracker (`EVD-2026-04-09-001`).
- **Persistence consistency (schema.sql):** Verified — `10_schema.sql`'s three tables (`habits`, `daily_reviews`, `habit_results`) match `10_architecture.json`'s Data Model field-for-field, including the `uq_habits_display_order ... deferrable initially immediate` constraint used by the reorder transaction and the `ck_habits_end_date_after_active_from` backstop check. Ownership is unambiguous (`private_application_state`, single owner, no shared contract).
- **Layer correctness:** Verified — day-state semantics, the merge/frozen-display rule, and the reporting cell-state derivations are HabitTracker-specific domain vocabulary; no reusable capability is exposed and no platform-layer leakage is present. `classification.not_platform` correctly justifies this.
- **Security (R-OPS-BP-02):** Verified — host binding `127.0.0.1:8027:8000` (least exposure), and port 8027 is confirmed free against `.claude/supportDocs/atlas_dev_ref.md`'s full port listing (no other component currently claims 8027).
- **UI test coverage:** `10_scaffolding.json` lists `src/ShellEntry.tsx` (`.tsx`, changed) in scope; `10_test_spec.md` contains three `[UI — manual]` scenarios describing observable user-facing behavior (status indicator, no-data-loss-on-navigation, grid drill-through). Requirement satisfied.
