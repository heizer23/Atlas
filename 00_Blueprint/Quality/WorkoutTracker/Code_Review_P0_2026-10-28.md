## Non-Blocking Issues

| # | Location | Observation |
|---|----------|-------------|
| 1 | `src/ShellEntry.tsx:393-396` vs `backend/routers/workout.py:296-297,328,336` | **Repeat bypasses the declared time authority (R-CON-AL-06).** `start_session` says the client's local date is the authority and `CURRENT_DATE` is only a fallback. SessionView sends `workout_date: localDate()` (`SessionView.tsx:77`), but Log → Repeat sends only `{split, from_session_id}`. The DB runs in UTC, so a Repeat between local 00:00 and 01:00/02:00 (CET/CEST) saves the session and every planned row under **yesterday's** date. Fix: send `workout_date` from Repeat too (and consider making it required). |
| 2 | `migrations/003_session_lifecycle.sql:42,72` | **Null weight is compared as "same weight".** `weight_kg is not distinct from prev_weight` gives a delta between two null-weight entries, and the comment says "NULL = bodyweight matches NULL". The spec says a missing weight must not be read as bodyweight. No impact on prod today (no exercise mixes null and non-null weights; 74/175 rows have null weight, all on exercises that never have a weight). Still, choose one: (a) require both weights to be non-null for a delta, or (b) keep the current behavior and remove "bodyweight" from the comment and spec. The test suite has no null-weight case either way. |
| 3 | `src/ExerciseLogView.tsx:100-104,135-137` | **A stale draft can overwrite newer server data.** A draft is written on mount, before any edit, and wins over `row` on the next open. It is cleared only on Save, Cancel or Delete. Scenario: open exercise X on the phone, leave via the bottom nav (draft stays, and `workout_open_exercise` reopens X automatically), save X on the desktop, return to the phone. The phone shows the old values, and Save sends them back over the newer row. The app advertises multi-device resume (`SessionView.tsx:7-8`), so this path is reachable. Fix: persist only once the form is dirty, or store the row's `updated_at` with the draft and drop the draft on mismatch. |
| 4 | `backend/routers/workout.py:307-330` | **Double start, check-then-insert.** Two concurrent starts both pass `_fetch_active`. The unique index stops the second insert (no data harm), but it then surfaces as a 500 `UniqueViolation`, not `409 ACTIVE_SESSION_EXISTS`. That bypasses the client's resume branch (`SessionView.tsx:80-84`). Catch `psycopg2.errors.UniqueViolation` and map it to 409. |
| 5 | `backend/routers/workout.py:310-311,331-342` | `from_session_id` is not validated. A well-formed but unknown id silently creates an empty session (should return 404). A non-UUID id returns a 500 (the transaction rolls back correctly). The same applies to a malformed `workout_date`. |
| 6 | `backend/routers/workout.py:476-490` | **`add_exercise` does not check session state.** (a) `status:"planned"` is accepted for finished or legacy sessions, which leaves a planned row that `finish` will never clean up. It is hidden from history and counts but still listed. (b) Finish runs concurrently with add on a second device: if finish deletes the empty session row between add's SELECT and INSERT, the new row becomes a session-less "legacy" workout. Single-user, so low probability. Restrict `planned` to active sessions. |
| 7 | `backend/routers/workout.py:155-157` vs `:270,317` | Split matching is inconsistent. Archetypes and template lookup use `LOWER(TRIM(split))`; the `split` filter on `GET /sessions` uses `LOWER(l.split)` with no TRIM. Prod has `'Ganzkörper '` (trailing space, 2 sessions), so `?split=Ganzkörper` returns nothing. The UI does not use the filter yet. |
| 8 | `src/ExerciseLogView.tsx:164-172,191,198,314` | **Wrong "last time" when editing an older session in Log.** `earlier` includes occurrences *after* the edited row, so "Last time", the stepper bases, the set placeholders and the chart all use the newest session, and the live column is drawn after newer sessions. The line also pairs `row.delta` (against the real predecessor) with that wrong `last`. The old code did the same (`HEAD ShellEntry.tsx:283`). In the Session tab this is correct, because the active row is the newest. |
| 9 | `tests/` | **Test gaps.** No test for Repeat via `from_session_id`: the spec says Repeat must create a new session and must not copy results, and only the implicit-template path is tested. `test_legacy_sessions_unchanged_by_migration` seeds rows *after* the migration, so it tests the column default, not migrating existing rows (the prod apply is the real evidence). No null-weight delta case, no 409-race case. **Not run:** `atlas-workout-tracker-test` has no `tests/` directory (its image predates the tests), and the conftest needs a throwaway container. No results are claimed. |
| 10 | `tests/ui/session_flow.spec.ts:4-7,93-95` | The UI test writes to the live DB: a real active session, then a finished `done` row with "UI test note". Cleanup runs in `finally`, but a killed run (timeout or container stop) leaves an active session behind, and the next real start would resume it. Also, the session is created before `createdId` is captured (`:38-39`), so a failure in that gap is never cleaned up. Acceptable for a solo app; prefer `atlas_test` (least exposure, R-OPS-BP-02 spirit). |
| 11 | `02_Platform/Atlas_Shell/dist/index.html` (mtime 1793211580) vs `src/ExerciseLogView.tsx`, `src/workoutShared.tsx` | **Frontend deploy unverified:** both sources are newer than `dist/` (~170 s). The Stop hook should rebuild; confirm after it runs. No nginx or Dockerfile changes. |
| 12 | `backend/routers/workout.py:515-546` | `PATCH /exercises/{id}` is a full replacement: an omitted field clears it, the same as explicit null, and the call now also forces `status='done'`. This is consistent today because the only caller always sends every field, with null to clear (`ExerciseLogView.tsx:211-220`). R-CON-AL-04 still asks for the omit-vs-null behavior to be stated; a one-line docstring covers it. |
| 13 | `schema.sql` (component root) | It still declares `ck_at_least_one_set` and has no `status` column or `workout_session` table. It is not wired anywhere, but if someone rebuilds from it, planned rows will be rejected. Delete it or mark it superseded by `migrations/`. |
| 14 | `src/workoutShared.tsx:309-376`, `src/SessionView.tsx:186` | Minor accessibility gaps: `ConfirmDialog` has no Escape handling and no initial focus or focus trap. The overview row's `aria-label` overrides its content, so the delta and chart summary are never announced. Touch targets in the new views meet 44 px (checked by the UI test). |

Checked and fine: route ordering (no path collisions between `/sessions/active`, `/sessions/start`, `/sessions/{id}/…`, `/exercises/names|history|{id}`). All new GETs (`/sessions/active`, `/archetypes`, `/exercises/names`) return `Dataset`, and mutations return `Dataset` or `ApiError` (R-CON-BP-04). The `list_sessions` f-string SQL is built only from constant fragments, with values bound as parameters. `finish` is atomic and its deletion of planned rows is confirmed in the UI. Discard, session delete and exercise delete all go through `ConfirmDialog`. Planned rows never show deltas (excluded in the view, plus the `DeltaChip` `completed` gate). Repeat copies only exercise + weight. `RequestValidationError` is now mapped to `ApiError` by the platform (`logFastapi.py:16`).

## Approval Condition

No blocking items, so the change is commit-safe as is. Recommended before or soon after commit:
1. Send `workout_date: localDate()` from Log → Repeat (`ShellEntry.tsx:395`). This is the only finding that persists wrong data.
2. Decide on null-weight delta semantics and align `003_session_lifecycle.sql:42,72` with the spec, plus one test.
3. Confirm that `dist/` was rebuilt after the last `.tsx` edits.
The remaining non-blocking items (#3–#10, #12–#14) can be handled during normal use; #3 (stale draft) is the most valuable of them.
